# iOS Build Time Optimization Report (ZStream / pstream-app)

## Applied (2026-08-29)

Baseline cold build: ~11 min. The following low-risk, high-impact caches were added to `.github/workflows/ios-build.yml` (commit after the auth fix):
- Dropped `pod install --repo-update` -> plain `pod install` (avoids re-fetching the multi-GB spec repo every run).
- Cache `node_modules` (key: `package-lock.json`).
- Cache CocoaPods spec repo `~/.cocoapods/repos`.
- Cache `Pods/` + `~/Library/Caches/CocoaPods` (key: `Podfile` + `Podfile.lock`).
- Cache `DerivedData` (`app/ios/build`) keyed on Xcode version + lockfiles.

Note: `Podfile.lock` is NOT committed to the repo (it is generated by `pod install` in CI). Cache keys therefore fall back to `Podfile` when the lockfile is absent. On a fully cold cache, plain `pod install` still resolves fine because modern CocoaPods uses the CDN by default. Expected warm build: ~4-6 min (down from ~11).

Not yet applied (higher risk / optional): Bundler for cocoapods gem (uses `app/Gemfile`), `ccache` (needs `compiler_check=content` + `USE_CCACHE=1`), RN precompiled binaries (`RCT_USE_PREBUILT_RNCORE=1`). Only apply after verifying the current caches, and commit `Podfile.lock` for deterministic fast resolves.

## 1. Is an 11-minute iOS build normal?

**Yes — 11 minutes cold is squarely normal for a React Native 0.82 app on a fresh GitHub Actions macOS runner.** `macos-15` (and all GH Actions macOS runners) are ephemeral: every job starts from a bare image with no persistent local cache. So you are paying the full "cold" cost on *every* run. Nothing about your 11 minutes is unusual.

Typical cold-build breakdown for an RN 0.82 app compiling ~80 pods (New Architecture, Hermes, static linkage — which is your setup since `USE_FRAMEWORKS` is not set):

| Phase | Typical cold time | Shares of the 11 min |
|---|---|---|
| Checkout | 10–30 s | small |
| setup-node + `npm ci` (fresh `node_modules`, ~330 MB) | 1–2 min | ~15% |
| `gem install cocoapods` | 30 s – 1.5 min (builds native ext) | ~8% |
| **`pod install --repo-update`** | **2–4 min** (spec repo fetch + pod resolution + downloading Hermes/RN prebuilt tarballs from Maven) | ~25–35% |
| **`xcodebuild`** (native + Swift + C++ compile of RN core + ~80 pods, plus Release JS bundling + Hermes compile) | **5–8 min** | ~55–60% |
| Packaging/upload | 10–30 s | small |

Key context about your specific slowness:

- **`pod install --repo-update`** is the single most avoidable slow step. `--repo-update` forces CocoaPods to re-fetch/reconcile the **entire CocoaPods spec repo** (`~/.cocoapods/repos/cocoapods`, a multi-GB git checkout) on every run — even though your `Podfile.lock` is already committed and versions are frozen. Modern CocoaPods uses the **CDN** (Trunk) by default, so a plain `pod install` only does small incremental metadata fetches, not a full clone. `--repo-update` negates that benefit.
- **`xcodebuild`** dominates because GH runners are ephemeral: `DerivedData` is deleted between runs, so you recompile ~80 pods + RN C++ from scratch every time. This is the biggest and most predictable target for caching.
- **`gem install cocoapods`** recompiles the cocoapods gem + native extensions every run.
- **`npm ci`** always re-downloads + re-extracts the full dependency tree from the GH Actions npm cache (setup-node already caches `~/.npm`, which helps, but `npm ci` still re-materializes `node_modules`).

For comparison, a warm, cached, incremental CI setup of an RN 0.82 app typically runs in **3–5 minutes**, and with `ccache` + React Native's experimental **precompiled (`RCT_USE_PREBUILT_RNCORE=1`) binaries** it can drop toward **2–3 minutes**.

## 2. Highest-impact optimizations (evaluated)

### 2.1 Cache `DerivedData` via `actions/cache` — HIGH impact
GH runners are ephemeral, but `actions/cache` persists a compressed tarball across runs in GH's blob storage (10 GB limit per repo, LRU-evicted). By keying on your lock files + Xcode version, `actions/cache` **restores the previous `DerivedData`**, so `xcodebuild`'s own incremental logic only recompiles what actually changed. Your build already uses `-derivedDataPath build`, which is a **contiguous, self-contained directory** — that's exactly what you want to cache.

- Save/restore `app/ios/build` (your `-derivedDataPath`).
- Include Xcode major version in the key (Xcode 16.4 vs future versions have incompatible module caches → always cache-miss if mixed).
- **Do not** use `restore-keys` as an exact-match fallback for DerivedData — a stale/`restore-keys`-matched DerivedData + project changes can produce "poisoned" incremental state. Prefer an exact key for DD, or use `restore-keys` only as a last resort and be ready to purge (`gh cache delete --all`).

> Caveat: DD caches can be several GB. Watch the 10 GB repo cache budget. Cache the `build` dir, not the whole default `~/Library/Developer/Xcode/DerivedData`.

### 2.2 Cache CocoaPods — HIGH impact
Two related things to cache:

**(a) The spec repo, `~/.cocoapods/repos/cocoapods`.** This is what `--repo-update` re-fetches. Caching it (keyed on CocoaPods version) avoids re-cloning the multi-GB spec repo.

**(b) The `Pods/` directory + CocoaPods download cache.** Key on `Podfile.lock` hash. Restoring `Pods/` makes `pod install` essentially a no-op (fast integrity check) instead of re-downloading + re-linking all pod source. Also include `~/Library/Caches/CocoaPods` so tarball downloads (Hermes + RN prebuilt `.tar.gz` from Maven, which are large — tens of MB each) are reused.

**The `pod install` vs `--repo-update` distinction:**
- `pod install` — uses the pinned versions in your committed `Podfile.lock` and the spec repos already on disk. Does minimal work. This is what CI **should** run.
- `pod install --repo-update` — first runs `pod repo update` (full spec-repo fetch/merge) **before** resolving. Slow, and generally **unnecessary in CI** because:
  1. You commit `Podfile.lock`, pinning every version.
  2. You never `pod update` individual pods in CI, so you never need newer specs than what produced the lockfile.
  3. CocoaPods already uses the CDN by default.

**Is dropping `--repo-update` safe?** In *your* workflow: **yes for the regular push/CI path**, because `Podfile.lock` is committed and you're only rebuilding what's already locked. The resolver uses the specs already present (restored from cache), and since versions are frozen by the lockfile, it won't try to fetch anything new. Keep the spec-repo cache warm so the specs that the lockfile references are always present.

> The only time you want `--repo-update` (or `pod update`) is when you've deliberately changed dependencies. That's a rare, manual, intentional action — not a daily build.

### 2.3 Cache npm — MEDIUM impact
`actions/setup-node@v4` with `cache: 'npm'` already caches `~/.npm` (the download cache). That makes `npm ci` much faster (no re-download), but `npm ci` still re-extracts ~330 MB of `node_modules`. You can additionally **cache `app/node_modules`**, keyed on `package-lock.json` hash, to skip the extraction. This is optional — the setup-node cache already captures the largest cost.

### 2.4 Cache the CocoaPods gem / `gem install cocoapods` — MEDIUM impact
Switch from raw `gem install cocoapods` to **Bundler** (`ruby/setup-ruby@v1` with `bundler-cache: true`) — which you already have infrastructure for (your `Gemfile` + `.bundle/config` are set up and there's a `Gemfile.lock` convention). `ruby/setup-ruby` restores installed gems from cache keyed on `Gemfile.lock`, so `gem`/native extension compilation is skipped on warm runs. This also pins your CocoaPods version deterministically (better than the current untracked `gem install cocoapods`, which installs "latest" and can drift).

Note: your `.bundle/config` sets `BUNDLE_PATH: "vendor/bundle"` — that's fine; `ruby/setup-ruby` caches that vendor path.

### 2.5 `xcodebuild` closed-source incremental / DerivedData reuse — HIGH impact
This is essentially the same as §2.1. There is no public "closed-source incremental" flag you're missing; Xcode's incremental build **is** the DerivedData mechanism. `-derivedDataPath build` + restoring `build` via `actions/cache` is the correct, supported way to get incremental reuse on ephemeral CI. (Xcode 15+ has a "progressive audit" incremental build enabled by default — it works automatically once DerivedData persists.) There's no separate flag to enable; just make sure DerivedData survives between runs.

### 2.6 Device-only architecture — MEDIUM impact (may already be satisfied)
You build with `-sdk iphoneos` (device), already `ONLY_ACTIVE_ARCH = YES` in the pbxproj, and no `-destination` with a simulator. So you're not compiling simulator slices — good. `EXCLUDED_ARCHS` is empty for device, which is correct for an IPA. **No change needed here.** (If you ever build a fat binary, you'd add `EXCLUDED_ARCHS[sdk=iphoneos*]` — but you don't currently.)

### 2.7 `ccache` — HIGH impact (biggest lever after DerivedData/pods)
RN's official guidance (reactnative.dev/docs/build-speed) recommends `ccache` for iOS native builds. RN 0.82 has built-in ccache support via the Podfile flag `:ccache_enabled => true` (currently **commented out** in your Podfile) or the `USE_CCACHE=1` env var at `pod install` time. ccache wraps `clang`/`clang++`, caches object files in `~/Library/Caches/ccache`, and survives clean DerivedData — so it's the standard, robust way to get very fast rebuilds on ephemeral CI.

Practical guidance for 0.82:
- Install ccache (`brew install ccache`) **before** `pod install`, then run `pod install` with `USE_CCACHE=1` so the Xcode project gets the ccache build settings.
- Cache `~/Library/Caches/ccache` via `actions/cache` (e.g. with `hendrikmuhs/ccache-action@v1.2`).
- **Important caveat (validated by 0.81/0.82-era reports):** ccache relies on file timestamps for hits, which breaks on CI because files get new mtimes every checkout. You MUST set `compiler_check=content` (i.e. hash file content, not mtime) for reliable CI hits. React Native's shipped `ccache.conf` historically uses mtime; RN PR #48257/#58066 (in 0.82-era) routes the correct `ccache` binary and config into the project so it works, but verify `ccache -s` on CI shows a high hit rate.
- If a clean-build CI cadence is more important than warm-cache speed, note RN recommends *not* needing ccache on CI if you can rely on DerivedData incremental — but since you're doing single-arch device builds and want to cut every minute, ccache + DerivedData together give the best result.
- *Alternative / complementary:* RN 0.81+ ships **experimental precompiled iOS builds**. Since you're on 0.82, you can reduce the huge RN-core + dependencies C++ compile by running `pod install` with:
  ```
  RCT_USE_RN_DEP=1 RCT_USE_PREBUILT_RNCORE=1 bundle exec pod install
  ```
  This downloads prebuilt XCFrameworks instead of compiling GLog/Folly/ReactNativeCxxCore from source — cutting the biggest part of `xcodebuild`. It's opt-in and experimental in 0.82; verify it works with third-party pods like `react-native-video`, `react-native-mmkv`, etc. (they may still compile from source, but RN core — the bulk — becomes prebuilt).

### 2.8 JS bundling / `SKIP_BUNDLING` — MEDIUM impact
Your Release `xcodebuild` runs the "Bundle React Native code and images" shell phase, which runs Metro to produce `main.jsbundle` + Hermes bytecode compilation **inside the Xcode build**. It's a single, relatively quick step (~20–60 s), but you can:
- **Pre-bundle once** and pass `ENTRY_FILE`/`SKIP_BUNDLING=1` at build time so xcodebuild only embeds the JS you already produced. Cache the `.jsbundle`/`.hbc`. This mostly helps if bundling is slow/repeated; for a small app it's a modest win.
- Use `SKIP_BUNDLING=1` in debug-only local flows — but your workflow is `Release`, so bundling runs regardless. If you want to skip it entirely, you'd need to provide a pre-built bundle.
- This is a secondary optimization; the native compile dominates, not the JS bundle. I'd rank it below DerivedData/pods/ccache.

### 2.9 GH Actions-native speedups — MEDIUM
- `actions/cache@v4` with a **content-addressed key** (`hashFiles(...)`) is the correct approach. Content-addressed keys hit exactly and don't suffer the "immutable cache, static key" stalls that `run_id`-based keys cause.
- `actions/cache@v5` (unified restore+save) is now available and is what current RN core CI uses; it reduces boilerplate.
- Right-size `max-size` on ccache and watch the 10 GB repo cache budget.
- Consider `xcbeautify --renderer github-actions` to cut log-processing overhead (minor).

## 3. Concrete recommended improvements (`ios-build.yml` plan)

Below is the exact plan. **Nothing has been applied — this is the recommendation.**

### 3.1 Steps to change

1. **Replace `gem install cocoapods` with Bundler** (`ruby/setup-ruby@v1` + `bundle install` with cache). Leverages your existing `Gemfile`.
2. **Cache CocoaPods**: spec repo `~/.cocoapods/repos` + `app/ios/Pods` + `~/Library/Caches/CocoaPods`.
3. **Drop `--repo-update`** → run plain `pod install`.
4. **Install ccache** and cache `~/Library/Caches/ccache`; set `:ccache_enabled` (or `USE_CCACHE=1`) and `compiler_check=content`.
5. **Cache `DerivedData`** (`app/ios/build`).
6. (Optional) Cache `app/node_modules`; keep setup-node npm cache.
7. (Optional, more invasive) Enable RN precompiled binaries via `RCT_USE_RN_DEP=1 RCT_USE_PREBUILT_RNCORE=1`.

### 3.2 Recommended cache key/restore strategy

| Cache | Path(s) to save | Key | restore-keys |
|---|---|---|---|
| Node (setup-node) | `~/.npm` | `npm-${{ hashFiles('app/package-lock.json') }}` (managed by setup-node) | — |
| node_modules (optional) | `app/node_modules` | `node_modules-${{ hashFiles('app/package-lock.json') }}` | `node_modules-` |
| Ruby gems | vendor/bundle (via setup-ruby) | `ruby-${{ hashFiles('app/Gemfile.lock') }}` | `ruby-` |
| CocoaPods spec repo | `~/.cocoapods/repos` | `cocoapods-${{ env.COCOAPODS_VERSION }}` | `cocoapods-` |
| Pods + pod caches | `app/ios/Pods` + `~/Library/Caches/CocoaPods` | `pods-${{ hashFiles('app/ios/Podfile.lock','app/Gemfile.lock') }}` | `pods-` |
| ccache | `~/Library/Caches/ccache` (via ccache-action) | `ccache-xcode16.4-${{ hashFiles('app/ios/Podfile.lock') }}` | `ccache-` |
| DerivedData | `app/ios/build` | `dd-xcode16.4-${{ hashFiles('app/ios/Podfile.lock','app/package-lock.json') }}` | `dd-xcode16.4-` |

Rules:
- **Pods**: exact key, no `restore-keys` fallback (a stale Pods dir breaks builds — Pods must match the lockfile exactly). Never let `pod install` with a different lock overwrite a cache.
- **DerivedData**: exact key primarily; `restore-keys` prefix allowed as a heuristic, but prefer exact to avoid poisoned incremental state. Include `env.XCODE_VERSION` in the key.
- **ccache**: `restore-keys` prefix is fine and desirable (partial hits useful).
- Watch total repo cache budget of **10 GB** — DerivedData + ccache can be large; don't cache the full default `DerivedData`, only your `build/` dir.

### 3.3 Whether to drop `--repo-update`

**Yes.** With `Podfile.lock` committed and only building locked versions, plain `pod install` (with the spec-repo cache) is correct and safe. Reserve `pod repo update` / `pod update` for intentional dependency bumps (manual, separate job). Expected saving: **~1.5–3 minutes per run**.

### 3.4 Expected time savings (per cold GH Actions run)

| Optimization | Expected saving |
|---|---|
| Drop `--repo-update` + cache spec repo | ~2–3 min (was the re-fetch) |
| Cache `Pods/` + `~/Library/Caches/CocoaPods` | ~1–2 min (no re-download/re-link) |
| Bundler + cache CocoaPods gem | ~30–60 s (no gem rebuild) |
| Cache `DerivedData` (`build/`) | ~2–4 min (incremental native build) |
| `ccache` (with content-check) | ~2–4 min additional on native compile |
| RN precompiled binaries (optional) | ~2–4 min on native compile (replaces much of RN C++) |
| Cache `node_modules` (optional) | ~10–30 s |

### 3.5 Realistic end-state

- **With the basic caches (Pods + DerivedData + Bundler, drop `--repo-update`): expect ~4–5 minutes.** 
- **With `ccache` added (and `compiler_check=content`): expect ~3–4 minutes.**
- **With RN precompiled binaries additionally enabled: expect ~2–3 minutes.**

The first three wins (drop `--repo-update`, cache Pods, cache DerivedData) are low-risk and give the biggest, most reliable gains immediately. `ccache` and precompiled RN are higher-value but need verification (ccache hit-rate check; precompiled compatibility with your pod stack).

### 3.6 Illustrative cache step snippets

```yaml
      - name: Select Xcode
        run: |
          sudo xcode-select -s /Applications/Xcode_16.4.app || true
          echo "XCODE_VERSION=16.4" >> "$GITHUB_ENV"

      - name: Setup Ruby + Bundler (cached gems)
        uses: ruby/setup-ruby@v1
        with:
          ruby-version: '3.4'          # match your runtime
          bundler-cache: true
          working-directory: app

      - name: Install ccache
        uses: hendrikmuhs/ccache-action@v1.2
        with:
          key: ccache-xcode${{ env.XCODE_VERSION }}-${{ hashFiles('app/ios/Podfile.lock') }}
          max-size: 2G
          append-timestamp: false
        # Then ensure content-based hits (RN ccache support expects content hashing on CI):
        #   echo "CCACHE_SLOPPINESS=..." / compiler_check=content (see build-speed docs)

      - name: Restore CocoaPods spec repo
        uses: actions/cache@v4
        with:
          path: ~/.cocoapods/repos
          key: cocoapods-${{ runner.os }}-${{ env.XCODE_VERSION }}
          restore-keys: |
            cocoapods-${{ runner.os }}-

      - name: Restore Pods + pod download cache
        id: pods-cache
        uses: actions/cache@v4
        with:
          path: |
            app/ios/Pods
            ~/Library/Caches/CocoaPods
          key: pods-${{ runner.os }}-${{ hashFiles('app/ios/Podfile.lock', 'app/Gemfile.lock') }}

      - name: Install CocoaPods dependencies  # NOTE: no --repo-update
        working-directory: app/ios
        run: bundle exec pod install

      - name: Restore DerivedData (build/)
        id: dd-cache
        uses: actions/cache@v4
        with:
          path: app/ios/build
          key: dd-xcode${{ env.XCODE_VERSION }}-${{ hashFiles('app/ios/Podfile.lock', 'app/package-lock.json') }}
          restore-keys: |
            dd-xcode${{ env.XCODE_VERSION }}-

      - name: Build app (no signing)
        working-directory: app/ios
        run: |
          USE_CCACHE=1 \
          xcodebuild \
            -workspace pstream.xcworkspace \
            -scheme ZStream \
            -configuration Release \
            -sdk iphoneos \
            -derivedDataPath build \
            CODE_SIGNING_ALLOWED=NO \
            CODE_SIGNING_REQUIRED=NO \
            build
```

*(Optional) For precompiled RN, change the pod step to:*
```yaml
      - name: Install CocoaPods dependencies (precompiled RN)
        run: |
          RCT_USE_RN_DEP=1 RCT_USE_PREBUILT_RNCORE=1 bundle exec pod install
```

## 4. Summary

- 11 minutes cold is **normal**; it's the ephemeral CI-tax (cold `--repo-update`, cold `Pods`, cold `DerivedData`, cold gem/npm).
- The single biggest, most reliable win is **dropping `--repo-update` + caching `Pods/` and `DerivedData`**.
- Add **Bundler (cached gems)** and **`ccache` (with content-hash checking)** for the next tier.
- **Realistic goal: ~3–5 minutes**; with RN precompiled binaries, ~**2–3 minutes**.
- Implement in this order (lowest risk first): (1) drop `--repo-update`, (2) cache Pods + spec repo, (3) cache DerivedData, (4) Bundler, (5) ccache, (6) precompiled RN.

**Note:** Re-run `pod install` (`USE_CCACHE=1`) once locally and confirm `ccache -s` shows high cacheable-call hit rates on CI before relying on it.
